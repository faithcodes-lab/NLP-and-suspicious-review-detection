# Suspicious Review Detection Web App Deployment

### 1. Model Architecture

**Sentiment Model**
- Architecture: DistilBERT (a lightweight version of BERT)
- Task: Binary text classification, Positive vs Negative
- Input: Raw review text
- Output: Label (Positive/Negative) and confidence score guage chart 

**Suspicious Review Model**
- Architecture: Logistic Regression 
- Task: Binary classification, Suspicious vs Not Suspicious
- Input: four structured features
- Output: Label (Suspicious/Not Suspicious) and confidence score guage chart 

---

### 2. The Four Structured Features

The logistic regression model was trained on four engineered structured features

| Feature | How it was computed |
|---|---|
| `review_frequency` | Total number of reviews posted by that reviewer |
| `unverified_ratio` | Whether the purchase was verified (0, 0.5, or 1) |
| `extreme_rating_ratio` | Whether the rating was 1 or 5 stars |
| `very_short_review` | Whether the review had fewer than 20 words |

`review_frequency` was computed as:
```python
df["review_frequency"] = df.groupby("reviewerID")["reviewerID"].transform("count")
```

---

### 3. The Core Problem: Training-Serving Skew

**What was discovered:**
When a new review is pasted into the app, the model has no information about who wrote it. `review_frequency` was hardcoded to `1` as a placeholder, which meant the model was silently degraded at inference time, effectively running as a three-feature model instead of four.

**Why this was serious:**
Feature ablation results showed that removing `review_frequency` caused F1 and Recall for suspicious reviews to drop to exactly zero — the most dominant feature in the entire model.

| Removed Feature | F1 (Class 1) | Recall (Class 1) |
|---|---|---|
| None (Baseline) | 0.066430 | 0.036469 |
| review_frequency | 0.000000 | 0.000000 |
| unverified_ratio | 0.013786 | 0.007168 |

This is a classic **training-serving skew** problem, the feature existed during training but not at inference point.

---

### 4. Investigating the Feature Distribution

Running descriptive statistics on `review_frequency` in the training data revealed:

```
count    827,398
mean     1.641024
median   1.0
mode     1
75th %   2.0
max      30.0
```

This was significant, the median and mode were both `1`, meaning hardcoding to `1` was actually the correct population prior. However, the principled approach is to load this dynamically from data rather than hardcode it.

---

### 5. considered solution: Reviewer Lookup Table

**Two fixes were implemented in priority order:**

**Immediate fix:** Replace the hardcoded `1` with the training data median loaded dynamically from reviewer stats JSON file.

**Short-term fix:** Add a Reviewer ID input field. If the ID is found in the training data lookup table, use the real historical frequency. If not found or left blank, fall back to the median.

**Implementation:**

A script was written to generate `reviewer_stats.json` from the training data:


The resolution logic at inference time follows this order:
1. Reviewer ID found in lookup: use real historical count
2. Reviewer ID provided but not found: use training median plus give a warning 
3. No Reviewer ID provided: use training median + info note

---

### 6. Industry Context

It was identified this is a known industry problem with established solutions:

| Solution | Description | Feasibility for this project |
|---|---|---|
| Feature store (Feast/Redis) | Pre-compute reviewer stats, serve at inference via key lookup | requires too much infrastructure |
| Review enrichment at ingestion | Compute stats when review is submitted, persist them | Requires user authentication and a database |
| Lightweight lookup table | Pre-compute from training data, serve via JSON |  Implemented |
| Population median fallback | Use training median when reviewer is unknown |  Implemented as fallback |

The implemented lookup table is architecturally equivalent to a lightweight feature store, the same pattern used at Uber, Airbnb, and Amazon, just without the Redis infrastructure.

---

### 7. Reviewer ID Format Limitation

A real-world limitation was discovered during testing. Modern Amazon reviewer IDs use the format `amzn1.account.XXXXX` while the training dataset uses the legacy format `AXXXXXXXX`. These are from different Amazon account systems with no public mapping between them.

This means the lookup table works correctly for reviewers in the training data but will never match real-world modern Amazon reviewer IDs. The fallback to the median handles this gracefully.

For the project writeup this is documented as an external data limitation, not an architectural flaw.

The original implementation used `shap.Explainer` which threw a `TypeError` with logistic regression on sparse matrices. This was fixed by switching to `shap.LinearExplainer` which is specifically designed for linear models.

After the suspicous review and sentiment models have been deployed, recent Issues were Identified and they were resolved through the following steps:

### Issue 1: SHAP Values Showing Zero for All Structured Features

During testing of the web application, all four structured features displayed SHAP values of +0.0000 or -0.0000, meaning the model appeared to give no weight to any of the engineered features. This was misleading because feature ablation had already proven that review_frequency alone caused F1 and recall to drop to zero when removed.
Investigation revealed two root causes. 

First, the structured features were not scaled before being combined with TF-IDF features. TF-IDF produces thousands of weighted dimensions whereas the structured features operate on a 0 to 1 or small integer scale. Without scaling, the structured features were numerically insignificant in comparison. 

Second, the SHAP explainer was being initialised with a single sample as the background distribution rather than the full training data. When a single sample is used as the background, SHAP measures the deviation of that same sample from itself, which is always zero.
The fix required two changes. StandardScaler was applied to the structured features before combining them with TF-IDF, and the full training data was used as the SHAP background distribution. 

After these changes, the structured features showed meaningful SHAP contributions for thge review analysed:  unverified_ratio at +1.10, review_frequency at +0.197, and extreme_rating_ratio at -0.264.

### Issue 2: TF-IDF Features Introducing Noise

After fixing the SHAP values, the top feature importance chart still showed TF-IDF words such as "crate", "downton", "outlander", "france", and "orphan" dominating the model's coefficients. These words have no obvious relationship with suspicious reviewing behaviour and suggested the model was learning product category patterns rather than genuine fraud signals.

Word frequency analysis confirmed this many of the most prominent words in suspicious reviews were related to specific product categories including books, TV shows, and kitchen products. This indicated the model was capturing spurious correlations between certain product types and the suspicious label.

The fix was to filter the TF-IDF vocabulary to retain only words with a meaningful frequency difference between suspicious and non-suspicious reviews. A threshold of 0.001 was applied to the class frequency difference, reducing the vocabulary from thousands of features to 278 meaningful discriminative words. This reduced noise while retaining genuine text signals.

After filtering, the model coefficients for the structured features became more competitive relative to the TF-IDF features, and the SHAP values remained meaningful.

### Issue 3: Feature Scale Caption Was Misleading

The web application displayed a caption stating that all structured features were on a 0 to 1 scale. This was accurate for binary features such as unverified_ratio, extreme_rating_ratio, and very_short_review. However when a reviewer ID was found in the lookup table, review_frequency reflected the reviewer's actual historical posting count which could exceed 1. For example, a reviewer with 4 historical reviews would show review_frequency = 4 on the chart despite the caption claiming a 0 to 1 scale.

The caption was updated to clarify that binary features operate on a 0 to 1 scale while review_frequency reflects the reviewer's actual historical posting count.
